# ValidateItems Automatic Null Checks

## Rationale

`Validator<T>` and `AsyncValidator<T>` already integrate automatic null handling into their public and child-validation pipelines: when a `null` source value is encountered, they ask the active `ValidationContext` to create the configured automatic null error and then stop further validation. The `ValidateItems(...)` helpers in `CheckExtensions.cs` currently diverge from that behavior. All reference-type collection overloads route through `GetRequiredCollectionValue(check)` and throw `InvalidOperationException` when the collection is `null`, even though the surrounding validation run may be configured to emit the standard automatic null error instead.

This plan aligns collection item-validation with the existing validator semantics. A `null` collection should participate in the automatic null-error pipeline by default, short-circuit behavior must remain unchanged, and the fallback behavior when the active automatic-null provider declines to create an error must be explicit and documented because item validation cannot proceed without a materialized collection instance.

## Acceptance Criteria

- [x] Every `ValidateItems(...)` and `ValidateItemsAsync(...)` overload in `CheckExtensions.cs` that currently depends on `GetRequiredCollectionValue(check)` performs automatic null handling before attempting to enumerate, mutate, or transform the collection.
- [x] When such an overload receives a `null` collection on a non-short-circuited check and the active `ValidationContextOptions.AutomaticNullErrorProvider` produces an error, the method adds that automatic null error for the collection target and returns `ValidatedValue<...>.NoValue` instead of throwing.
- [x] The automatic null error produced by `ValidateItems*` uses the same target-resolution and display-name semantics as validators do today, including caller-expression handling and target-prefix composition.
- [x] Short-circuited `ValidateItems*` calls still return `ValidatedValue<...>.NoValue` immediately and do not invoke item validators, delegates, cancellation checks, or automatic null handling.
- [x] When a non-short-circuited `ValidateItems*` call encounters a `null` collection, it does not invoke item validators, delegate callbacks, normalization logic, enumeration, mutation, or cancellation checks before either returning `ValidatedValue<...>.NoValue` or throwing the documented fallback exception.
- [x] When the active `AutomaticNullErrorProvider` declines to create an error for a `null` collection, `ValidateItems*` has a clearly documented fallback so callers are told to guard explicitly with `IsNotNull()` before validating items.
- [x] XML documentation in `CheckExtensions.cs` is updated to remove the blanket instruction that nullable collections must always be guarded explicitly, and instead explains the automatic-null behavior and the remaining explicit-guard scenario.
- [x] Automated tests cover synchronous and asynchronous validator-based overloads, synchronous and asynchronous delegate-based overloads, short-circuit behavior, the provider-declined fallback path, and the emitted error target/message shape for `null` collections.

## Technical Details

The implementation should stay inside `CheckExtensions.cs` and centralize the null-collection behavior in one private helper instead of duplicating it across the overload families. The helper should be used by every overload that currently calls `GetRequiredCollectionValue(check)`, which includes the mutable, read-only, delegate-based, transforming, and asynchronous collection-validation overloads. `ImmutableArray<T>` overloads do not require collection-level automatic null handling because the collection itself is a value type, so they should only be touched where comments or XML docs need clarification.

The helper should mirror the validator pipeline as closely as `Check<T>` allows. After argument-null checks and after the existing short-circuit early return, it should inspect `check.Value`. When the collection is non-null, validation continues exactly as today. When the collection is `null`, it should derive the display name for the collection using the same base-name expression that `CreateIndexedDisplayName` already uses: `check.DisplayName ?? check.Target`. Because `TryCreateAutomaticNullError` requires a non-null display name string, passing this resolved value directly keeps the `NotNull` definition, message caching, target normalization, and caller-expression special case consistent with `Validator<T>` and `AsyncValidator<T>`. The helper should then signal the calling overload to return `ValidatedValue<...>.NoValue` without invoking item validators or delegates. A `bool`-returning signature that mirrors `BaseValidator.TryHandleAutomaticNull` is the idiomatic pattern — for example: `private static bool TryHandleNullCollection<TCollection>(Check<TCollection> check, [NotNullWhen(false)] out TCollection? collection)` — where a `false` return means the collection is null and the error has already been added (or the fallback exception thrown).

Because `ValidateItems*` cannot continue without a collection instance, the provider-declined path needs to be deliberate. If `TryCreateAutomaticNullError(...)` returns `false`, the helper should preserve an exception-based fallback with a clearer message than the current generic null-collection exception. The message should explain that the active automatic-null provider did not create an error for the current validation run and that callers must guard with `IsNotNull()` before calling `ValidateItems(...)` or `ValidateItemsAsync(...)`. This is the one place where `ValidateItems*` cannot behave exactly like a validator that can still delegate to custom validation logic after automatic null handling produces no error.

Update the XML docs and exception documentation for the affected overloads to reflect the new contract. The current remarks that nullable collections must be guarded explicitly should change to: automatic null handling is attempted first; explicit guards are still required when the active automatic-null provider does not emit an error and the caller wants deterministic non-exceptional behavior. The private `GetRequiredCollectionValue(...)` helper can either be replaced entirely or narrowed to the post-automatic-null fallback path, but the final structure should make it obvious that automatic null handling is the first branch.

Test coverage should be expanded in the existing collection-focused test fixtures rather than in isolated implementation-detail tests. Convert the current default-context “throws when collection is null” expectations in `CollectionValidationWorkflowTests.cs` into assertions that a single automatic null error is added and `ValidatedValue<...>.NoValue` is returned. Add dedicated tests that create a context with `NoOpAutomaticNullErrorProvider.Instance` and `NoOpValueNormalizer.Instance` to verify the documented fallback exception for both synchronous and asynchronous `ValidateItems*` overloads. Add short-circuit tests for `null` collections that prove no error is added and no delegate or validator is invoked. Add non-short-circuited `null`-collection tests that prove delegates, validators, normalization, enumeration, mutation, and async cancellation checks are all skipped on the null path. For async overloads, also verify that null-collection handling completes before any enumeration work or cancellation checks begin.
