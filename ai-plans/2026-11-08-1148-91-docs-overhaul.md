# Split the README into a focused walkthrough and topic docs

*Frozen at 2026-11-08T11:48Z*

## Rationale

`README.md` has 1,519 lines and works as pitch, tutorial and reference at the same time. The library's main promise — a `Result<T>` survives the trip across a process boundary — is never shown in one piece: returning a result, validating input, writing the HTTP response and reading it back as `Result<T>` are hundreds of lines apart. At the same time, large parts of the public API are not documented at all (metadata annotations, HTTP headers, enrichers, the built-in check catalog, error overrides, message templates and more), and some existing statements are inaccurate.

The goal is a short README that tells one coherent story and links to a new `docs/` folder, which keeps all existing information and fills the known gaps. This is done in one PR.

### Gaps to fill

Take the content from the source and its XML docs. The plans in `ai-plans/` explain the intent behind most features.

- **Core:** `MetadataValueAnnotation` (where a value is serialized: HTTP body, HTTP header, CloudEvents `data`, extension attribute), `MetadataObjectBuilder`/`MetadataArrayBuilder`, `MetadataKind` and the number kinds, `MetadataMergeStrategy`, `MergeMetadata`, the `Tracing` extensions, working with `Errors`, and that `default(Result<T>)` is neither success nor failure and is rejected at write boundaries.
- **HTTP:** writing metadata as response headers (`HttpHeaderConverter`, `DefaultHttpHeaderConversionService`, `HttpHeaderValueFormatter`), reading headers (selection strategies, `HttpHeaderParser` and its registry, `HeaderValueParsingMode`, `HeaderConflictStrategy`), `IHttpResultEnricher`, `CreateProblemDetailsInfo`, status code selection with mixed categories, and wire examples for `AspNetCoreCompatible`, `MetadataSerializationMode.Always` and a `404` problem.
- **CloudEvents:** wire examples for a success and a failure envelope, how failure is detected on read, `IdResolver`, `CloudEventsAttributeParser`, and configuration through `IOptions`.
- **Validation:** the full catalog of built-in checks with codes (`ValidationErrorCodes`) and metadata keys (`ValidationErrorMetadataKeys`), `ErrorOverrides`, message templates and localization, how targets are built (`ValidationTargetCasing`, `DisplayName`), short-circuiting, `Custom(...)`, the `AddError` overloads, and value normalizers.
- **OpenAPI:** the diagnostics reference, MVC customization of generated contracts, and `ValidationErrorContractAttribute`/`ValidationErrorMetadataContractAttribute` for custom checks.

### Performance claim

The numbers come from the existing tables, comparing `LightPortableResults` with `FluentValidationSingleton`: speed 2.1x (flat valid) to 6.2x (flat invalid), allocations 7.8% (complex invalid) to 22% (complex valid). Singleton is the fair baseline because the docs recommend singleton validators for both libraries. `docs/benchmarks.md` states this baseline above the tables.

### Tests

Add a new test project `tests/Light.PortableResults.Documentation.Tests` to `Light.PortableResults.slnx`, referencing the Minimal APIs and Validation packages. It holds the walkthrough tests and the link check. Do not put these tests into `Light.PortableResults.Tests`, because that changes the mutation-testing smoke-check vector in `tests/mutation-testing.md`.

The walkthrough test hosts the app in-process like the `IntegrationTests` apps in `Light.PortableResults.AspNetCore.MinimalApis.Tests`. Test-only host setup, such as the test server, lives outside the code that the README shows, so the verbatim check can hold. The README test and the link check find the repository root by walking up to `Light.PortableResults.slnx`; they need no network access.

The link check computes heading anchors with GitHub's slug rules and also accepts explicit `<a id="...">` anchors. Links to other hosts are not checked.

The source generator help-link test goes into `Light.PortableResults.Validation.OpenApi.SourceGeneration.Tests`. `DiagnosticDescriptors` currently uses one shared `HelpLinkBase` that points to a README anchor that does not exist.

### Packaging

`src/Directory.Build.props` packs the root `README.md` into every package, which is why its links must be absolute. There are no public API changes, so no compatibility suppressions are needed. The source generator ships inside `Light.PortableResults.Validation.OpenApi`, which is why that package gets the release note.
